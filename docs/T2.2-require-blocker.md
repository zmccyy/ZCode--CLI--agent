# T2.2 阻塞问题：require() 相对路径解析

## 现状

当前仓库已经明确分成两条启动链路：

- `ZCode/src/entrypoints/publicCli.js`：公共、稳定、面向 Node.js 的最小 CLI 入口
- `ZCode/src/entrypoints/cli.tsx`：面向 Bun 的完整 REPL / TUI 主链路

因此，T2.2 不再追求“Node.js 下跑通完整 `cli.tsx -> main.tsx -> REPL.tsx`”。
方案 A 的完成目标改为：

1. Node.js 继续稳定承载公共 CLI：`--help` / `doctor` / `models` / `-p --json`
2. Bun 作为完整主链路运行时，负责启动 `src/entrypoints/cli.tsx`
3. 文档与测试都清晰表达这条运行时边界

## 为什么不继续攻 Node 完整兼容

**`require()` 相对路径解析在 `tsx + Node.js ESM` 下不适合作为完整主链路兼容方案。**

验证过程：

1. tsx 单独运行 `.ts` 文件时，`require("fs")` 包路径可用，但 `require("./module.js")` 相对路径失败
2. tsx 内部用虚拟文件 `src/noop.js` 作为 require 的调用栈基准路径，所有相对 require 都从中解析，路径必然错误
3. 自定义 loader 的 `load` hook 无法拦截 tsx 处理的 `.ts` 文件——tsx 在 loader 链中短路，注入的 `createRequire` 包装不生效
4. `createRequire(fileURL)` 直接调用时是正常的——问题不在 `createRequire`，在于无法把 per-module 的 require 注入到 tsx 处理后的模块作用域

受影响代码模式分布广泛，且大量用于同步懒加载、循环依赖切断、功能门控：

```typescript
// src/utils/permissions/permissionRuleParser.ts:13
require('../../tools/BriefTool/prompt.js') as typeof import('../../tools/BriefTool/prompt.js')

// src/constants/prompts.ts:80
require('../tools/BriefTool/prompt.js') as typeof import('../tools/BriefTool/prompt.js')

// src/utils/config.ts:33-42
require('../memdir/teamMemPaths.js') as typeof import('../memdir/teamMemPaths.js')

// src/main.tsx 等多处
require('./tools/BriefTool/prompt.js') as typeof import('./tools/BriefTool/prompt.js')
```

这些 `require()` 大多包裹在箭头函数或 feature gate 中，用于同步懒加载和打破循环依赖。即使局部可替换，系统性改造成本仍然偏高。

## 评估过的方向

### 方案 A：Bun 负责完整主链路（采用）

- 思路：不再让 Node.js 承担完整 REPL 主链路；Node.js 仅保留公共 CLI 入口，完整 `cli.tsx` 链路由 Bun 运行
- Bun 原生支持 ESM 模块中使用 `require()`，更接近历史代码的运行时假设
- 目标命令：`bun src/entrypoints/cli.tsx --help`
- 优点：
  - 与代码库历史结构一致
  - 避免继续堆叠脆弱的 Node loader / require polyfill
  - 可以把精力集中到真正的 Bun 启动 blocker，而不是假兼容层
- 缺点：
  - 完整 REPL 不在 Node.js 下承诺
  - 需要单独维护 Bun 本地开发与安装说明

### 方案 B：`tsc` 预编译后再由 Node 运行

- 思路：放弃 tsx，用 `tsc` 将 TS 预编译成 JS（CommonJS 输出），再用 Node 直接跑
- 需要配置 tsconfig（`"module": "commonjs"`），加 build step
- 优点：require 在 CJS 下原生可用
- 缺点：需要 build step，开发体验下降；ESM 的 import 语法也可能需要调整

### 方案 C：批量改造 `require()` → 动态 `import()`

- 思路：把所有 `require()` 调用改成 `await import()`
- 缺点：
  - `import()` 是异步的，现有同步懒加载模式（箭头函数包裹）会被破坏
  - 改动量大，约 20+ 处需要修改且需要传播 async
  - 代码库设计为同步懒加载，改为异步可能引入新的启动顺序问题

### 方案 D：全局 `require` 替代 + 调用栈路径映射

- 思路：提供一个全局的 `require` 函数，内部根据 Error.stack 获取调用者文件路径来正确解析相对路径
- 缺点：依赖 `Error.stack` 解析，脆弱且在不同 Node 版本间不稳定；被箭头函数包裹后调用栈可能不正确

## 采用结论

采用 **方案 A**，但要把边界说清楚：

- Node.js 目标面：公共 CLI，不负责完整 REPL
- Bun 目标面：完整 `cli.tsx -> main.tsx -> REPL.tsx` 启动链路

这意味着 T2.2 后续工作的重点不再是继续修补 Node.js 的 `require()` 兼容层，而是：

1. 修正文档与测试，明确双入口定位
2. 清理 Bun 主链路的真实 blocker（依赖、缺模块、运行时错误）
3. 以 Bun 启动成功作为 T2.2 的验收标准

如果未来“Node.js 必须运行完整 REPL”成为新硬需求，再单独立项走方案 B；不建议继续投入方案 D。
