结论

我梳理后的判断是：这个问题的“最佳解”不是继续补 Node 的 require() polyfill，而是先把运行时边界定清楚。

当前仓库实际上已经分成两条链路：

稳定公共入口是 publicCli.js (line 1) -> publicCliCore.js (line 206)。这条链路明确只承诺 --help、doctor、models、-p --json，而且帮助文案里已经写了“不启动完整 TUI”。
完整交互链路是 cli.tsx -> main.tsx -> REPL.tsx，它在计划文档里被单独列为后续 P0 工作，而不是当前公共 CLI 契约的一部分：zcode-detailed-development-plan-v2.md (line 14)、zcode-detailed-development-plan-v2.md (line 110)。
对你这份 md 的判断

T2.2-require-blocker.md (line 1) 里对 tsx + Node ESM + 相对 require() 的判断基本是对的。仓库里的两条尝试也说明了这一点：

globals.js (line 13) 用的是一个全局 createRequire(...)，它只能有一个固定基准路径，天然不知道“当前模块是谁”。
loader.js (line 69) 试图做 per-module 注入，但这条路和 tsx 的装载方式是错位的。
我还用 ctx7 查了 tsx 文档。tsx 官方给的做法是：在 ESM 里显式从 tsx/cjs/api 引入 require，并把 import.meta.url 作为上下文传进去，而不是依赖一个全局 ambient require 自动推断调用者路径。这一点直接支持你的结论：
tsx require docs

另外，最新仓库里这个问题也不是唯一 blocker。我实测：

node src/entrypoints/publicCli.js --help 正常。
bun src/entrypoints/cli.tsx --help 当前先卡在 lodash-es/memoize.js 依赖解析，不是只卡 require()。
我建议的最佳方案

最佳方案是“方案 A，但加上目标重定义”：

Node 只承诺公共 CLI。
Bun 承诺完整 REPL 主链路。
不再继续投入“全局 require polyfill + loader 注入”这条线。
原因很直接：

这和现有代码分层、测试契约、README、计划文档是一致的。
继续攻 Node 完整兼容，收益低，且 require() 只是主链路问题之一。
真正该推进的是 Bun 下把 cli.tsx -> main.tsx -> REPL.tsx 跑通。
如果以后“Node 必须跑完整 REPL”变成硬需求，那才开新任务走“方案 B 家族”的构建产物路线；不要继续押注方案 D，也不建议现在大规模把同步 require() 改成异步 import()。

我没有全量重跑测试，只做了入口级和运行时级 smoke 验证。
如果你认可这个方向，我下一步可以直接把这份 T2.2 文档和开发计划改写成这个结论，并顺手列出 Bun 主链路的真实 blocker 清单。
